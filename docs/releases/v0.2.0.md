# Vedrfolnir v0.2.0  -  experimental preview

**Historical notes from the old repository.** Artifacts and publication
statements below describe that preview, not releases in the recreated
`HRAshton/vedrfolnir` repository. See [current candidate notes](v0.3.0.md).

**Status: prerelease / alpha. Not certified for production scheduling commitments.**

Vedrfolnir predicts time remaining to a terminal multi-job build/workflow
result using historical job durations, visible queued/running work and
observed infrastructure contention. It does not execute jobs or need a GPU.

## Included

- CPU-only FastAPI and local SQLite, with optional read-only SQL Server or
  CSV data adapters and source-contract preflight.
- Historical-duration fallback plus observed VM or pool-aware priority/FIFO
  queue replay. Dynamically discovered pools have ten-minute historical
  capacity refresh, per-poll live pressure and optional declared slot limits.
- Shared River model as a **shadow-first** bounded residual corrector;
  promotion requires meaningful completed-build MAE/tail improvements.
- Empirical P90 upper ETA only with at least 40 comparable completed forecasts;
  diagnostics include evidence warnings, MAE, signed bias and measured coverage.
- Seeded virtual-clock simulator, public-trace evaluators and documented
  results (including failures).

## Quick installation

Docker Compose v2 (the initial image build compiles checksum-verified
**stable CPython 3.15.0** because the official `python:3.15-slim` tag was
not yet published when the release was prepared):

Docker Compose v2:

~~~bash
cp .env.example .env
# Replace ETA_ADMIN_TOKEN with a long random token
docker compose up -d --build
curl http://localhost:8080/api/status
~~~

Only the Python wheel and sdist are attached to this release; there is **no prebuilt Docker image**. Compose builds the container locally.

CPython **3.15 only**; install the attached `vedrfolnir-0.2.0-py3-none-any.whl`
with pip, or from source with `python -m pip install -e .`.

Use `SOURCE_MODE=demo` for synthetic data, `SOURCE_MODE=files` for normalized
CSV, or `SOURCE_MODE=mssql` after installing the MSSQL extra and mapping
the SELECT-only SQL source contract. See [quick start](../quickstart.md)
and [SQL/CSV columns](../contracts.md).

## Accuracy limits: read before use

In real KTH SP2 and CTC SP2 **single-job queue traces**, historical baselines
substantially underestimated elapsed time. The River promotion gate abstained
on both. Real Nextflow and Pegasus workflow-start traces also failed to
justify River selection. These targets **do not establish accuracy of the
multi-job pool-aware scheduler**.

New three-seed synthetic pool simulations improved on the legacy heuristic,
but **declared capacity did not outperform inferred capacity** in those
workloads, and congestion drift still introduced strong optimistic bias.
See [observations](../observations.md).

Not implemented: SQL dependency graphs, resource reservations/preemption,
unknown future arrivals, configurable scheduling policies or automatic
arbitrary `feat_*` SQL columns. P90 bounds are empirical, not guarantees.

The read API/UI has no authentication: restrict to localhost or add an
authenticated TLS proxy. Sync requires a bearer token. Use a SELECT-only
source SQL user. One application worker/SQLite writer is supported.
No external MSSQL installation was validated by this release.

## First startup behavior

The Docker image compiles the stable Python 3.15 release from verified
upstream source until the corresponding official stable slim base exists.
This first build requires internet access to the Python source and PyPI.
After the container starts, check `GET /api/status` for
`data_source_sync: recent`; the initial import and model initialization
can take longer than HTTP process startup.

## Validation and compatibility

Published artifacts must pass CPython 3.15 unit/River tests, wheel/sdist
build and installed resource checks, **Docker demo + CSV API/start/restart
smoke**, and legacy SQLite upgrade/backup tests.

The release is tagged only after the actual Docker image passes HTTP
startup/restart checks on both synthetic demo data and a fresh CSV source.
Passing these packaging checks is **not** a claim of validated prediction
accuracy on unfamiliar schedulers.

This first experimental preview is **not a guarantee of stable API/SQL
compatibility**. Pool migration is additive; arbitrary schema migrations
and pickle checkpoint compatibility across dependency versions are not
guaranteed. No automatic PyPI publication.

See the [release roadmap](../roadmap.md) for evidence needed before 1.0.
