# Individual job ETA  -  local implementation checks, October 13, 2026

Base: `851ebf7ee8f330cab09b78f78985c71514b23e0e` (eligibility diagnostics).
Local runtime: stable CPython 3.15.0, SQLAlchemy 2.0.54 and real River 0.26.1.
This implementation exposes dispatch/finish from the existing allocation;
it does not retune duration estimation, workflow calibration or River.

## Replay observations

All **1,053 workflow prediction rows** remained identical to the previously
recorded base runs: 400 original CSV, 471 FIFO control and 182 Snakemake rows.
The additional job forecasts score first observations per run ID and observed
status, after the same plan warmup. Completed job labels are attached only
at completion. No later eligible snapshot replaces an unavailable first one.

| Original synthetic CSV, queued jobs | 289 | 289 | 8.969 | 11.418 | 21.309 | -11.087 |
| Original synthetic CSV, running jobs | 247 | 247 |  -  | 5.513 | 11.945 | -2.365 |
| Synthetic two-slot FIFO control, queued jobs | 120 | 120 | 46.117 | 46.704 | 85.050 | +44.054 |

Times are minutes. Original CSV queued-wait P90 error was 15.000 and signed
bias -8.969; FIFO-control wait P90 was 85.000 and bias +43.083. The original
CSV has 253 first pending observations and Snakemake has 7,456, all withheld.
Snakemake has **zero queued observations** because no admission times exist.

The original CSV's whole-workflow first forecasts are still 0/40 eligible;
an individual admitted job can now be forecast despite a pending sibling.
Availability is a functionality result, **not an accuracy improvement**.
The original fixture's waits are independently generated, not enforced by
an actual finite-capacity dispatcher; its errors do not establish scheduler
fidelity. The FIFO control does enforce two slots, but its deep backlog
exposes accumulated duration-estimation error and strong late bias.

Snakemake provenance: `wfcommons/WfInstances` commit
`d7bfead08a4dbf985ebbf427b3685a6512c259e2`, `snakemake/`, 34 accepted files,
29 scored plans after five warmups. This reuses previously examined public
data and its measured task-span proxy; it is not a fresh independent holdout.
Its running-job results cannot validate queue-wait prediction.

Every job forecast has `river_used=false` and no P90 upper ETA. Job-level
coverage is **unmeasured**. Different targets/sources are not pooled; counts
are correlated jobs, not independent workflows. Fixed plan-relative snapshot
offsets can miss brief queued or running phases.

## Operational scope and next evidence

`bash scripts/local_check.sh full` passed locally: Ruff, **148 tests with real
River**, four simulator smoke runs, wheel/sdist build and installed-wheel
version/API/static-resource checks. As in the prior investigation, a writable
`TMPDIR` and the active venv dependency directory in `PYTHONPATH` were supplied
for the restricted runtime's nested wheel-verification environment. The
installed Starlette emits a TestClient/httpx deprecation notice; it did not
skip or fail any tests. HTTP tests use the real FastAPI routes and SQLite.

HTTP tests exercise filtered global competition, queued jobs with pending
siblings, standalone jobs, source error/staleness, timestamp persistence
across restart, invalid-snapshot rejection, paused/unknown capacity, future
admission isolation, unknown FIFO ordering and unsupported pool VM affinity.
Reading the API never stores predictions or modifies the poller's ML/cache.

This is not a real SQL Server or Docker deployment test. Live forecasts are
on-demand; a pilot still needs pre-outcome observations plus actual source
job start/finish exports and capacity records. The
[capture protocol](../job-forecasts.md#evaluate-and-prepare-a-real-pilot)
describes the required evidence. Queue policy and data freshness must be
verified on that installation before forecasting claims are made.
